# Vortex — native recompilation and decompilation

A port of Apple's iPod click-wheel game *Vortex* (`vortex_1_1_2563290.bin`, 2006 — a Breakout
played around a circle) to modern machines, the fifth title after *Mini Golf*, *Lost*, *Texas
Hold'em* and *The Sims Bowling*. The game is first **statically recompiled** — every ARM
function becomes a C++ function that runs the same instructions on a small CPU-state struct —
so it runs natively from day one. Functions are then **hand-decompiled** one at a time into
real, named, readable C++, each swap proven against the recompiled version. The iPod's
application frameworks (OpenGL ES, audio, file I/O, click wheel) are reimplemented as a host
library, `libeapp`, behind plain C++ interfaces (`src/framework/`), and the parts of all that
which belong to no single title are compiled from `../common` rather than copied here.

`PLAN.md` is the plan of record: what this game is, what it takes from the other four titles
and how, where it differs from them, and a progress log of what has been established. The
code-quality rules that bind every recomp are in `../Mini Golf/PLAN.md` § "Code quality"; read
them before contributing.

## Layout

```
PLAN.md                  the plan of record, with the schedule and the progress log
README.md                this file
CMakeLists.txt           build; targets `vortex` (SDL3) and `vortex-headless` (no window)
tools/
  survey.py              what is in the image — every number PLAN.md states
  funcs.py               seed the function table gen/funcs.json (vectors, live edges, pointers)
  emit.py                run the shared ARM → C++ recompiler (../common/tools/recomp) into gen/
  progress.py            how much of the game is still recompiled rather than decompiled
  manifest.py            the game folder's file table -> src/gamedata/manifest_data.cpp
  port-from-bowling.py   copy what is not yet shared from ../Sims Bowling, and record it
gen/                     GENERATED by emit.py, never hand-edited (gitignored)
src/
  runtime/               the eApp image, the frame pump (main.cpp), region sizes (memory.cpp);
                         cpu.h / runtime.h / memory.h forward to the shared core
  framework/             what the game may ask the platform to do — graphics (shared), audio,
                         storage, controls, device, music library. Plain C++, no ordinals
  libeapp/               the iPod frameworks on the host: files (async_file.cpp), audio, input,
                         misc, metadata; arm_abi.cpp adapts them to the ARM calling convention
                         for the recompiled code; imports.json is this title's ordinal table
  gamedata/              this title's file manifest; the zip reader is shared, the installer here
  game/                  hand-decompiled game code; grows as gen/ shrinks (empty so far)
  platform/sdl3/         window, audio, keyboard, the macOS settings window (desktop)
  platform/null/         no I/O (headless runs)
analysis/                the reverse-engineering evidence for this title (README.md there)
reference/               MANIFEST.md and PORTED.md, the provenance of what was copied in
```

## Windows

There is a 64-bit Windows build — `vortex.exe`, the same SDL3 program as the macOS one.

    tools/windows-build.sh

The toolchain is MinGW-w64. It is not installed on this machine and does not need to be: the
script — a wrapper around `../common/tools/windows-build.sh`, which every title shares — builds
an Ubuntu image with the cross-compiler, its zlib and SDL3's own mingw development package, and
runs the whole build in it against this working tree, so Docker is the only requirement. The
toolchain file beside it, `mingw-w64.cmake`, serves as well on any machine with the
`x86_64-w64-mingw32` toolchain on its path; on Windows itself `CMakeLists.txt` also spells every
option the MSVC way, so `cmake -B build` there is the other route. The result is
`build-windows/dist/`: `vortex.exe` beside the `SDL3.dll` it loads. Nothing else is needed — the
C++ runtime is linked in.

To run it, copy that folder to a Windows machine and start the .exe. On first launch it asks for
the game's files with the native file browser, as on macOS, and keeps them in
`%APPDATA%\iPod Vortex` beside the saves and settings. There is no console
window: the game is one window and nothing else. Started from a terminal it joins that terminal
and prints there as it always did, and anything fatal with no terminal to print to is a message
box, so a program that cannot start still says why
(`common/src/ipod/platform/windows_console.h`). The headless build is deliberately still
a console program, since its output is the whole point of it.

**Settings.** Ctrl+, opens the settings window — the same tabs as the Mac's, as a Win32 window of
the game's own (`src/platform/sdl3/win32_settings.cpp`), owned by the game's window so it stays
in front of it. Tab moves between the controls and Escape closes it. The two windows share
everything but the widgets: the actions, the keys on offer, the saved files and the hooks into
the host are the portable code behind both, so a change in one is a change in the other. Its
controls take the modern look from the manifest in `src/platform/sdl3/win32_settings.manifest`,
which the build embeds.

**Music** plays, through Media Foundation: the tracks are AAC, which SDL does not decode, and
the decoder behind `src/platform/sdl3/music_decoder.h` is AudioToolbox on macOS and a Media
Foundation source reader on Windows — each the system's own, so there is nothing to ship. A
Windows "N" edition without the Media Feature Pack has no AAC decoder; the program says so once
on the console and plays on without music.

## Releases

**The game's folder is `12345`.** That is the folder from the iPod that a player has to
supply; no artifact contains it, and nothing runs without it. Each built artifact carries a
readme that says so, names that folder, and gives the place it ends up
(`%APPDATA%\iPod Vortex\12345` on Windows, `~/Library/Application Support/iPod Vortex/12345`
on macOS).

    ../common/tools/release.sh <version> Vortex

builds every artifact this machine can and lays them out under `release/<version>/` with a
`SHA256SUMS` beside them:

    vortex-<version>-macos.zip         "Vortex.app", universal, macOS 11 and later
    vortex-<version>-windows-x64.zip   the .exe and SDL3.dll

The same script is what continuous integration runs (`.github/workflows/release.yml`), so a tag
and a laptop build the same thing. Run it with no title named and it does every title in the
tree. It signs nothing: an unsigned .app is quarantined by macOS the first time it is opened
from a download, and each artifact's readme says how to open it anyway (right-click ▸ Open, or
`xattr -dr com.apple.quarantine`). Signing needs a paid Apple developer account and is a
decision for whoever publishes.

The macOS artifact is built against SDL's own release framework rather than this machine's SDL,
which is what makes it universal and lets it run on macOS 11: a Homebrew SDL is built for the
machine it was installed on and would pin the app to that architecture and that macOS version.

## Building

Requirements: CMake ≥ 3.21, a C++17 compiler, Python 3.10+, SDL3 (via `pkg-config` or its
CMake package), zlib, and the game's folder — `12345`, 96 files, ~30 MB — which is not
included: it is the owner's game data.

```sh
python3 tools/funcs.py && python3 tools/emit.py      # gen/ — the recompiled game
cmake -B build && cmake --build build
./build/vortex                                       # asks for the game's folder the first time
./build/vortex --gamedir="PATH/12345"                # or run straight from a copy, unchecked
```

The windowed build is a bundle on macOS, so it lands at `build/vortex.app/Contents/MacOS/vortex`
rather than `build/vortex`; the headless build is a plain executable as before.

**The first command is not optional, and it needs your copy of the game.** `gen/` holds the
machine-translated half of this port: the functions that have not been decompiled by hand yet,
written out as C++ by the shared recompiler (`../common/tools/recomp`). It is not in the
repository and never will be, because it is a translation of the game's own binary rather than
anything written here. `tools/funcs.py` reads that binary and seeds the function table;
`tools/emit.py` walks it and writes `gen/src`. Both default to a copy of the game sitting beside
this tree, so point them at yours:

```sh
python3 tools/funcs.py --image "PATH/12345/Executables/vortex_1_1_2563290.bin"
python3 tools/emit.py
```

The `.bin` they want is inside the game's own `12345` folder, under `Executables/`, which is
the same folder the built game asks you for on its first run. Skip this step and CMake still
configures, the compile still succeeds, and the link fails with a wall of undefined symbols.


Release (`-O3 -g`, assertions kept) is the default and matters: the renderer is a software
rasteriser. `-DCMAKE_BUILD_TYPE=RelWithDebInfo` is `-O1 -g`, for stepping recompiled code.
`-DVORTEX_SANITIZE=ON` builds with ASan/UBSan.

The game's files are installed to the per-user data directory on first launch (macOS
`~/Library/Application Support/iPod Vortex/12345`; `VORTEX_DATA_DIR` overrides) and verified
against `src/gamedata/manifest_data.cpp` on every launch. `--install=PATH` installs from a
folder or zip without the dialog. The game writes three files of its own into its folder —
`options`, `stats` and `<lang>/stats` — which the manifest ignores.

The game runs at 30 frames a second by default, which is the rate the device ran it at and the
rate its own arithmetic needs (PLAN.md difference 5); `--fps=` changes it, and the clock the
game reads never advances by less than a 64th of a second per frame whatever the rate.

## Saves and leaving the game

Escape is the Menu button, which is how an iPod game is left: the game asks to be put away and
the program ends, saying so as it goes. That is not a crash and nothing is lost — the game writes
its save on the way out, and the next launch resumes it (`runtime/main.cpp` for the byte the
game answers in).

The game keeps four files of its own — `options`, `stats`, `<lang>/stats` and the saved game
`quick<name>` — and writes every one of them through the store calls when it is left, reading
them back at start-up. They live in the platform's save store, which by default is the game's own
folder. A run also prints one line about a guest access outside mapped memory: that is the game
reading a byte through a pointer it has not set yet, on its first frame, answered with zero.

## Debugging aids

`--original-assets` serves the game's files exactly as they ship, including the three mislabelled
texture headers that make the ENTER NAME glyphs draw as noise (`src/gamedata/asset_fixes.h`);
it is the way to see what the shipped data does.
`--call-log=FILE` (or `-`) writes the framework-call log; `--frames=N` stops after N frames;
`--time=HH:MM` fixes the clock; `--trace-entry=ADDR,...` prints the registers at every entry to
a recompiled function; `--dump-entry=` and `--dump-frame=` print guest memory at an entry or
after every frame; `--trace-from=FRAME` keeps the entry trace quiet until that frame, so every
function can be traced for one frame. `VORTEX_TRACE_FILES=1` prints one line per file operation.
`VORTEX_WATCH=ADDR` stops with a backtrace at the first store to a guest word while the entry
trace is on, `VORTEX_WATCH_VALUE=V` narrows it to one value, and `VORTEX_WATCH_LOG=1` turns it
into a running log instead. `VORTEX_TRACE_UNMAPPED=1` prints, with a host backtrace, every guest
access outside mapped memory (`src/runtime/memory.cpp`).

## Status

2026-08-28: the pure recompilation (753 functions, 39 247 instructions) runs natively — a
600-frame boot, the title screen, ENTER NAME, and a name entered, NEW GAME and the first level
played to GAME OVER, with every picture along the way drawn correctly.
Getting there needed one new entry point in the shared heap (`realloc`) and no change to the
shared recompiler. Two faults found by playing it
are fixed on top of that: the game is put away when it asks to be (Escape in the menus), and the
three mislabelled texture headers behind the corrupted ENTER NAME glyphs are corrected as they
are read. Nothing is hand-decompiled yet. `PLAN.md` § "Progress log" has the detail, and what is *not* yet established.
