# Cutting a release

Six games, three platforms, one script. `common/tools/release.sh <version>` builds every
artifact the machine it runs on can build and lays them out under `release/<version>/` with a
`SHA256SUMS` beside them. It is the only description of how an artifact is made: continuous
integration (`.github/workflows/release.yml`) calls it rather than repeating it, so a tag and a
laptop cannot produce different things.

    common/tools/release.sh 1.0.0                 # every title, every platform this machine can
    common/tools/release.sh 1.0.0 Vortex Lost     # only those two

## What comes out

One file per game per platform, named `<game>-<version>-<platform>.zip`, plus a source tarball.

| | |
|---|---|
| `<game>-<version>-macos.zip` | `<Game>.app`, universal (arm64 and x86_64), macOS 11 and later |
| `<game>-<version>-windows-x64.zip` | the `.exe` and `SDL3.dll` beside it |
| `<game>-<version>-switch.zip` | the `.nro` for the Homebrew Menu (Mini Golf only, so far) |
| `ipod-recomps-<version>-source.tar.gz` | `git archive` of the tag |

**The source tarball does not build on its own, and is not meant to.** Five of the six titles
compile machine-translated code from `<title>/gen/src`, which is not in the repository and never
should be: it is a mechanical translation of the original game's binary, regenerated by
`tools/funcs.py` and `tools/emit.py` from the owner's own copy of that game. So a fresh tree
builds Mini Golf, whose `src/game/` is the whole game by hand, and needs those two commands and
a copy of the game for each of the others. Each title's README says so as the first line of its
build instructions. The release notes should say it too, or somebody will report it as a bug.

**Architecture appears in a name only where it has to.** Windows is x64 alone, because Windows
on ARM emulates it. macOS is one universal file rather than two downloads. The Switch is
aarch64 and nothing else. Linux, if it is ever added, is the one platform that genuinely needs
`-x86_64` and `-aarch64` in the names, along with a decision about the oldest glibc to build
against.

Every artifact carries a `README.txt` written by `common/tools/artifact-readme.sh`, saying what
the game's own folder is called, where it has to go on that platform, and what to do about the
warning an unsigned program gets. Every artifact that contains SDL carries `SDL3-LICENSE.txt`,
because SDL's licence asks to travel with it (`common/licenses/`).

## Where each part can be built

    macOS      needs a Mac: Apple's linker and install_name_tool
    Windows    needs only Docker — the MinGW toolchain is in a container
    Switch     needs only Docker — devkitPro is in a container

So a Mac builds all three and a Linux runner builds the last two, which is exactly how the
workflow splits its jobs. Anything the machine cannot build is skipped with a line saying so,
and the run still succeeds; the checksums file lists what was actually made.

## The macOS build is not built against your SDL

A Homebrew SDL is built for the machine it was installed on: one architecture, and a minimum
macOS equal to whatever that machine runs. An app built against it runs on Apple silicon, on the
newest macOS, and nowhere else — which is fine for developing and useless for shipping. The
release script downloads SDL's own release framework instead, which is universal and asks only
for macOS 11, and caches it under `.release-cache/`. That is what makes the artifact universal.

## What it deliberately does not do

**It signs nothing.** An unsigned `.app` downloaded from the internet is quarantined by
Gatekeeper, and an unsigned `.exe` is met by SmartScreen. Each artifact's readme tells the
player how to open it anyway. Signing needs paid certificates from Apple and from a Windows
certificate authority, and secrets in the repository to use them; both are decisions for whoever
publishes rather than something a build script should assume. If they are ever wanted, they
belong at the end of `package_macos` and `package_windows`, and nowhere else.

## Before the first release

- [x] **A LICENSE file.** GPL-3.0-or-later for the games, MIT for `common/tools/`, copyright
      Brandon Smith. See `LICENSING.md`.
- [ ] Bump `project(... VERSION x.y.z ...)` in each title's `CMakeLists.txt`. That is the only
      place a version is written: from there it reaches the macOS bundle's `Info.plist` and the
      Switch's own metadata, both of which read `PROJECT_VERSION` rather than a literal. The
      version in an artifact's *name* is the argument to this script and is yours to keep in
      step with it.
- [ ] Tag it (`git tag v1.0.0`), so the source tarball is the tag rather than whatever `HEAD`
      happened to be. The script says which one it used.
- [ ] Push the tag. The workflow drafts the release with everything attached; read it before
      making it public.

## Adding a title, or a platform

`common/tools/titles.txt` is the list the script walks: one line per title giving its directory,
its executable, the name a person sees, the folder its game files live in, its data directory,
and the platforms it can be built for. A new title is a line there. A title that gains a Switch
port gains `switch` on its line, and nothing else changes.
